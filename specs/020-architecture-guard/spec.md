# Feature Specification: Правила слоёв под тестом, карта архитектуры, гигиена репозитория

**Feature Branch**: `020-architecture-guard`

**Created**: 2026-11-15

**Status**: Draft

**Input**: User description: "Рефакторинг инфраструктуры без изменения поведения: правила зависимостей между слоями
ставятся под тест, появляется краткая карта архитектуры, из репозитория убираются артефакты сборки. Сейчас тест

сохраняющий все нынешние проверки домена; документ docs/architecture.md со слоями, путями данных и чек-листами
типовых изменений; ссылки на него из CLAUDE.md и README.md; исключение артефактов сборки из git. Код приложения
между слоями не переносится; поведение не меняется; существующие тесты остаются зелёными. Подробности и
границы — docs/refactoring/step-7-architecture-guard.md и docs/refactoring-roadmap.md."

Шаг 7 плана рефакторинга (`docs/refactoring-roadmap.md`, `docs/refactoring/step-7-architecture-guard.md`).
Видимых изменений нет: код приложения не меняется, меняются только тесты, документы и настройки репозитория.

## User Scenarios & Testing *(mandatory)*

Пользователь этого шага — разработчик (человек или агент), который меняет код проекта. Пользовательница
приложения не должна заметить никакой разницы.

### User Story 1 - Правила слоёв проверяются тестом (Priority: P1)

Разработчик добавляет импорт, нарушающий правила слоёв из плана рефакторинга (например, хранилище обращается к
интерфейсу, отчёт — к хранилищу, домен — к библиотеке React или к часам). Один тест архитектуры сразу
становится красным и называет файл, импорт и нарушенное правило. Тест опирается на одну явную таблицу «слой →
разрешённые слои и пакеты» для всех слоёв, видит все формы импорта и проверяет каждый исходный файл
приложения. Все нынешние проверки домена при этом сохраняются.

**Why this priority**: сейчас граф импортов чистый, но для всех слоёв, кроме домена, держится на внимательности,
а тест домена не видит импортов без `from`, динамических импортов и слоёв `report` и `pwa`. Это основная цель
шага.

**Independent Test**: тест архитектуры зелёный на текущем коде; временный неверный импорт в каждом слое (и в
исходниках воркера) делает его красным с понятным сообщением, после отката — снова зелёный; распознавание
каждой формы импорта проверено отдельно на образцах текста.

**Acceptance Scenarios**:

1. **Given** текущий код, **When** запускаются тесты, **Then** тест архитектуры зелёный, и проверено столько
   файлов, сколько исходных файлов приложения есть в `src` (без тестов).
2. **Given** в файл хранилища временно добавлен импорт интерфейса, **When** запускаются тесты, **Then** тест
   красный и называет файл, импорт и правило «`storage` не может импортировать `ui`».
3. **Given** в доменный файл временно добавлен импорт без `from` (`import '../ui/…'`), динамический импорт
   (`import('../storage/…')`), повторный экспорт (`export … from '../push/…'`) или многострочный импорт,
   **When** запускаются тесты, **Then** каждый из них обнаружен.
4. **Given** в доменный файл временно добавлено чтение текущего времени (`new Date()` или `Date.now()`),
   **When** запускаются тесты, **Then** тест красный — как и прежде.
5. **Given** в слой, которому пакет не разрешён, временно добавлен импорт пакета (например, библиотеки дат в
   интерфейс или Dexie в отчёт), **When** запускаются тесты, **Then** тест красный.
6. **Given** в `src` появился новый каталог или файл верхнего уровня, которого нет в таблице слоёв, **When**
   запускаются тесты, **Then** тест красный и просит отнести файл к слою.
7. **Given** исходник воркера временно импортирует код приложения из `src`, **When** запускаются тесты,
   **Then** тест красный.
8. **Given** исключение из таблицы перестало быть нужным (импорта, ради которого оно записано, больше нет),
   **When** запускаются тесты, **Then** тест красный и просит удалить исключение.

### User Story 2 - Одна короткая актуальная карта архитектуры (Priority: P2)

Разработчик открывает `docs/architecture.md` и за пару минут понимает: какие есть слои и что каждому можно
импортировать; как данные читаются, записываются и уходят на воркер; как обновляется приложение и строится
отчёт; где живут правила корректности данных; что править, чтобы добавить настройку, отметку дня или вид
напоминания. Инструкция проекта (`CLAUDE.md`) и `README.md` ссылаются на этот документ, а не называют первую
фичу «текущей».

**Why this priority**: сведения сейчас разнесены по спецификациям 19 фич, часть устарела; добавление одной
настройки требует правок в шести местах, и список нигде не записан. Без карты каждое изменение начинается с
раскопок, но поведение это не меняет, поэтому P2.

**Independent Test**: документ существует, короче двух экранов, содержит все обязательные разделы; каждый
упомянутый в нём путь существует; список слоёв в нём совпадает с таблицей теста; `CLAUDE.md` и `README.md`
ссылаются на него, строки «Текущая фича» нет.

**Acceptance Scenarios**:

1. **Given** документ `docs/architecture.md`, **When** разработчик ищет, что можно импортировать слою
   `push`, **Then** находит это в таблице слоёв, совпадающей с таблицей теста, и ссылку на тест.
2. **Given** нужно добавить настройку, **When** разработчик открывает чек-лист «Добавить настройку», **Then**
   в нём перечислены все места правки (тип и значение по умолчанию, правило поля, миграция и версия схемы,
   экран, тесты) с путями к файлам и ссылка на чек-лист новой версии схемы.
3. **Given** документ ссылается на файл или каталог проекта, **When** запускаются тесты, **Then** путь
   существует.
4. **Given** `CLAUDE.md`, **When** агент читает «Ключевые документы», **Then** видит ссылку на карту
   архитектуры и не видит «Текущая фича: `specs/001-cycle-calendar/`».
5. **Given** агент запускает тесты, **When** читает раздел «Команды» `CLAUDE.md`, **Then** узнаёт, что
   Vitest запускается из PowerShell в папке проекта, а из Git Bash с `cd /c/…` падает целиком.

### User Story 3 - Репозиторий не хранит артефакты сборки, поиск тестов не молчит (Priority: P3)

После `npm run build` и `npm test` рабочее дерево остаётся чистым. Файл кэша компилятора не отслеживается и
игнорируется. Если шаблон поиска тестов перестанет находить тесты, запуск тестов завершится ошибкой, а не
пройдёт молча; тестовые файлы с разметкой (`*.test.tsx`) тоже находятся.

**Why this priority**: гигиена — дешёвая защита от случайных изменений и тихо пропущенных тестов, но на
поведение не влияет.

**Independent Test**: `git ls-files` не содержит файлов `*.tsbuildinfo`; `git status` после сборки и тестов
пуст (кроме неотслеживаемой папки `Claude outputs/`); в настройках тестов нет разрешения «проходить без
тестов»; число найденных тестов не меньше базового.

**Acceptance Scenarios**:

1. **Given** чистое дерево, **When** выполнены `npm run build` и `npm test`, **Then** `git status` ничего не
   показывает (кроме `Claude outputs/`).
2. **Given** файл `tsconfig.tsbuildinfo` есть на диске, **When** смотрится `git status`, **Then** он не
   показан — игнорируется.
3. **Given** шаблон поиска тестов не находит ни одного файла, **When** запускаются тесты, **Then** запуск
   завершается ошибкой.

### Edge Cases

- Многострочный импорт (`import {\n a,\n b,\n} from 'x'`) и импорт только типов (`import type …`,
  `export type … from`) считаются зависимостью наравне с обычными.
- Слово `import` или `from '…'` в комментарии или строковом литерале не считается импортом и не даёт ложного
  нарушения; если отличить нельзя — правило записывается так, чтобы не было ни пропусков, ни ложных
  срабатываний на текущем коде (решается в плане).
- Динамический импорт с вычисляемым именем (не литерал) в исходнике приложения проверить нельзя — тест
  считает его нарушением, если он не записан исключением.
- Подпуть пакета (`date-fns/locale`, `react-dom/client`) относится к своему пакету; модули `node:*` и
  виртуальные модули сборщика (`virtual:pwa-register`) — тоже пакеты и разрешаются явно.
- Импорт CSS в точке входа (`./ui/theme.css`) — зависимость от слоя `ui`.
- Файлы верхнего уровня `src` — точка входа приложения, точка входа service worker и файл объявлений типов —
  описаны в таблице явно, со своими правилами.
- Вспомогательный модуль тестов внутри слоя (`src/ui/testing.ts`) не является тестом по имени и проверяется по
  правилам своего слоя.
- Нормализация путей: импорт `../domain/x` из `src/storage` и `../../domain/x` из `src/storage/migrations`
  относятся к одному слою `domain`; импорт внутри слоя (`./x`, `../components/x` из `src/ui/screens`)
  разрешён всегда.
- Разделители путей Windows (`\`) не влияют на результат; регистр в путях сравнивается точно, как у
  компилятора.
- Тесты (`*.test.ts`, `*.test.tsx`) не проверяются: им разрешено импортировать что угодно, включая
  `node:fs` и другие слои.

## Requirements *(mandatory)*

### Functional Requirements

**Тест правил слоёв**

- **FR-001**: Правила зависимостей MUST проверяться одним тестом архитектуры с одной явной таблицей «слой →
  разрешённые слои приложения и разрешённые пакеты». Таблица MUST соответствовать разделу «Целевые правила
  слоёв» плана рефакторинга и покрывать слои `domain`, `storage`, `report`, `push`, `hooks`, `pwa`, `ui`,
  файлы верхнего уровня `src` (точка входа приложения, точка входа service worker, объявления типов) и
  исходники воркера.
- **FR-002**: Тест MUST проверять каждый исходный файл (`.ts`, `.tsx`) в `src` на любой глубине, кроме тестов.
  Каждый файл MUST относиться ровно к одному слою таблицы; файл вне таблицы MUST давать ошибку.
- **FR-003**: Тест MUST распознавать все формы импорта: `import … from '…'`, импорт без привязок `import '…'`,
  повторный экспорт `export … from '…'`, динамический `import('…')`, в том числе многострочные и только для
  типов. Распознавание MUST быть проверено тестами на образцах текста для каждой формы, написанными до кода.
- **FR-004**: Правила пакетов MUST проверяться той же таблицей: библиотека дат — только в домене; Dexie —
  только в хранилище, в хуке живых запросов и там, где он остался после шага 5 (синхронизация напоминаний);
  React — только в хуках, интерфейсе и точке входа. Пакет, не разрешённый слою явно, MUST давать ошибку.
- **FR-005**: Все проверки прежнего теста изоляции домена MUST сохраниться: домен не импортирует `react`,
  `react-dom`, `dexie`, `storage`, `ui`, `push`, `hooks` и не читает текущее время (`new Date()` без
  аргументов, `Date.now(`). Дополнительно домену MUST быть запрещены `report` и `pwa`. Заменяется ли прежний
  тест новым или остаётся рядом — решается в плане; ни одна его проверка не теряется.
- **FR-006**: Исключения MUST перечисляться в таблице явно — файл, импорт и причина, — а не ослаблением
  распознавания. Исключение, которому не соответствует ни один импорт, MUST давать ошибку.
- **FR-007**: Сообщение об ошибке MUST называть файл, импорт и нарушенное правило. Срабатывание MUST быть
  показано в ходе разработки временным неверным импортом в каждом слое и в воркере (красный → зелёный);
  временные нарушения MUST NOT попадать в репозиторий.
- **FR-008**: Если тест находит нарушение в текущем коде, код MUST NOT переноситься в этом шаге: работа
  останавливается, пользователю сообщается о нарушении.
- **FR-009**: Исходники воркера (`worker/src`) MUST NOT импортировать код приложения из `src`; тест
  архитектуры MUST это проверять. Тесты воркера не проверяются (контрактный тест — названное исключение
  шага 5).

**Карта архитектуры**

- **FR-010**: Документ `docs/architecture.md` MUST содержать: слои и их правила (со ссылкой на тест); пути
  данных — чтение через живые запросы, запись, синхронизация напоминаний, обновление приложения, отчёт для
  врача; где живут правила корректности данных; чек-листы «Добавить настройку», «Добавить отметку дня»,
  «Добавить вид напоминания»; ссылку на `src/storage/migrations/README.md`.
- **FR-011**: Документ MUST быть не длиннее двух экранов — не больше 120 строк.
- **FR-012**: Документ MUST описывать состояние после шагов 1–6, сверенное с кодом и «Журналом» плана, а не с
  файлами шагов. Пути к файлам и каталогам, упомянутые в документе, MUST существовать, а список слоёв в нём
  MUST совпадать со слоями таблицы теста — это проверяется тестом.

**Инструкция проекта и README**

- **FR-013**: `CLAUDE.md` MUST ссылаться на `docs/architecture.md` в «Ключевых документах»; строка «Текущая
  фича: `specs/001-cycle-calendar/`» MUST быть убрана; в «Командах» MUST появиться строка о запуске тестов
  из PowerShell (из Git Bash с `cd /c/…` Vitest падает целиком). Правила рабочего процесса в `CLAUDE.md`
  MUST NOT меняться. Итоговый текст правок `CLAUDE.md` MUST быть показан пользователю в отчёте.
- **FR-014**: `README.md` MUST ссылаться на `docs/architecture.md` в разделе «Разработка».

**Гигиена репозитория**

- **FR-015**: `tsconfig.tsbuildinfo` MUST NOT отслеживаться в git; файлы `*.tsbuildinfo` MUST игнорироваться.
  После `npm run build` и `npm test` `git status` MUST быть пустым (кроме `Claude outputs/`).
- **FR-016**: Настройки тестов MUST NOT разрешать успешный запуск без найденных тестов.
- **FR-017**: Шаблон поиска тестов MUST находить и файлы `*.test.tsx` (отложено сюда журналом шага 6: сейчас
  такой файл молча не запустился бы).

**Общие ограничения рефакторинга** (`docs/refactoring-roadmap.md`)

- **FR-018**: Поведение и дизайн MUST NOT меняться. Исходный код приложения в `src` (кроме тестов) и код
  `worker/` MUST NOT меняться вовсе: меняются только тесты, документы, `CLAUDE.md`, `README.md`,
  `.gitignore` и настройки тестов.
- **FR-019**: Существующие тесты MUST оставаться зелёными; существующие проверки MUST NOT удаляться или
  ослабляться — кроме разрешённой файлом шага замены теста изоляции домена с сохранением всех его проверок.
  Если нужно изменить другую существующую проверку — остановиться и спросить пользователя.
- **FR-020**: Схема хранения MUST NOT меняться: `SCHEMA_VERSION`, таблицы, форма хранимых записей и блоки
  `this.version(1…6)` в `src/storage/db.ts` — прежние.
- **FR-021**: Правила `CLAUDE.md` и Конституции MUST соблюдаться: TDD (тест распознавания импортов и тест
  карты пишутся первыми и падают), файлы — UTF-8 без BOM, правка только Edit/Write, проверка `git diff` на
  испорченную кириллицу перед коммитом, маленькие коммиты, каждый проходит `npm test` и `npm run build`.
  Новые runtime- и dev-зависимости (в том числе ESLint) MUST NOT добавляться.
- **FR-022**: Объём — только этот шаг: пункты 1–4 наброска из файла шага и FR-017. Не входят: перенос кода
  между слоями, ESLint, правка спецификаций прошлых фич, изменение правил рабочего процесса в `CLAUDE.md`,
  объединение других тестов, читающих исходники (`derivationPlacement`, `explanationTexts`,
  `uiLogicPlacement`, `dayWrites`, `validationPlacement`, `pushPlacement`, контрактный тест воркера), и
  правка тестов воркера. Попутные находки записываются в «Журнал» `docs/refactoring-roadmap.md`, а не
  исправляются.

### Key Entities

- **Слой**: каталог или набор файлов `src` (или `worker/src`) с общими правилами зависимостей.
- **Правило слоя**: разрешённые слои приложения и разрешённые пакеты; всё остальное запрещено.
- **Исключение**: конкретный файл, конкретный импорт и причина; должно соответствовать существующему импорту.
- **Импорт**: имя модуля из любой формы импорта; относится либо к слою (относительный путь), либо к пакету.
- **Карта архитектуры**: `docs/architecture.md` — слои, пути данных, места правил корректности, чек-листы.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Тест архитектуры проверяет 100 % исходных файлов `src` (без тестов) и `worker/src`; число
  проверенных файлов равно числу таких файлов; ни один файл не остаётся вне таблицы.
- **SC-002**: Каждая из четырёх форм импорта (с `from`, без привязок, повторный экспорт, динамический) и их
  многострочные и типовые варианты распознаются — подтверждается тестами на образцах, падавшими до реализации.
- **SC-003**: Временное нарушение в каждом из 7 слоёв, в файлах верхнего уровня и в воркере делает тест
  красным с именем файла, импорта и правила; после отката тест зелёный; в репозитории нарушений нет.
- **SC-004**: Каждая проверка прежнего теста изоляции домена (7 запретов импорта и 2 формы чтения часов)
  имеет соответствие в тестах после шага.
- **SC-005**: `docs/architecture.md` — не больше 120 строк, содержит все разделы FR-010; 0 несуществующих

## Assumptions

- «Два экрана» — не больше 120 строк документа при ширине строки около 110 символов, как в других документах
  проекта.
- Точка входа приложения (`src/main.tsx`) — место сборки: ей разрешены все слои и пакеты интерфейса. Точка
  входа service worker (`src/sw.ts`) — только `pwa` и пакеты Workbox. Файл объявлений типов
  (`src/vite-env.d.ts`) импортов не имеет; директивы `/// <reference …>` импортами не считаются.
- Слою `pwa` разрешён виртуальный модуль регистрации service worker (`virtual:pwa-register`) и не разрешены
  слои приложения.
- Синхронизация напоминаний (`src/push/sync.ts`) после шага 5 по-прежнему использует живые запросы Dexie;
  это записывается исключением с причиной, а не разрешением Dexie всему слою `push`.
- Импорт только типов считается зависимостью: связь слоёв через типы — тоже связь. Если окажется, что такой
  импорт нарушает правило, — это исключение с причиной или находка для пользователя (FR-008).
- Другие тесты, читающие исходники, частично повторяют правила слоёв (например, «нет `date-fns` в
  `src/ui`»), но остаются как есть: их объединение изменило бы существующие проверки (общее ограничение 2).
- Файл `tsconfig.tsbuildinfo` сборкой не обновляется (настройки компилятора — без вывода и без
  инкрементального режима); убирается только из git, на диске может остаться — его скроет `.gitignore`.
- Тесты и сборка запускаются из PowerShell в папке проекта (особенность окружения, `docs/refactoring-roadmap.md`).
