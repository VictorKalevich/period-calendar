# Research: Правила корректности настроек и месячных — в домене

Фича 016, шаг 3 плана рефакторинга. Пункты «Проверить на этапе плана» файла шага разобраны в R2 (неизвестные
поля настроек), R5 (месячные при чтении) и R8 (тексты ошибок импорта).

## R1. Правила настроек: `coerceSettings(raw, fallback)` в `src/domain/settings.ts`

**Decision**: новый файл `src/domain/settings.ts`. В нём таблица правил по полям (бывшая `SETTING_RULES` из
`backup.ts`, тип `{ readonly [K in keyof Settings]: (v: unknown) => boolean }`) и функция
`coerceSettings(raw: unknown, fallback: Readonly<Settings>): Settings`. Семантика — та же, что у
`parseSettings`: результат — копия `fallback`, поверх которой положены корректные известные поля `raw`.
Если `raw` — не объект, результат — копия `fallback`. Правила прежние: целое в диапазоне из
`CYCLE_LENGTH_RANGE`, `PERIOD_LENGTH_RANGE` и `OVULATION_SHIFT_RANGE` (границы включительно), остальные поля
— `typeof v === 'boolean'`. Импорт (`parseBackupUnsafe`) вызывает `coerceSettings(data.settings, current)`
вместо `parseSettings`.

**Rationale**:
- Правила — инварианты домена: диапазоны уже лежат в `src/domain/types.ts`, а теперь рядом с ними и
  проверки. Их можно тестировать без файла резервной копии и без базы (критерий готовности шага).
- Тип таблицы требует правила для каждого ключа `Settings`. Новая настройка без правила не соберётся.
- Результат — всегда новый объект, даже когда `raw` не объект. `parseSettings` в этом случае возвращал сам
  `current`; при импорте это ничего не меняет, потому что результат сравнивается по значению. Для чтения
  (R2) это важно: запасное значение там — замороженный `DEFAULT_SETTINGS`, а `getSettings` всегда отдавал
  новый незамороженный объект.
- Неизвестные поля `raw` в результат не попадают, а неизвестные поля `fallback` сохраняются — ровно как в
  `parseSettings` (`{ ...current }`, затем только известные ключи). Порядок полей — порядок `fallback`.

**Alternatives considered**:
- *Оставить правила в `backup.ts` и вызывать их оттуда при чтении*: `repository.ts` зависел бы от модуля
  резервной копии, а правила домена остались бы в хранилище. Отклонено, это и есть проблема шага.
- *Правила внутри `src/domain/types.ts`*: там типы и константы; функции с проверками лучше держать в
  отдельном файле с собственными тестами, по образцу `dayEntry.ts`.

## R2. Неизвестные поля и порядок полей при чтении из базы

**Decision**: в `src/domain/settings.ts` есть вторая функция `extraSettingFields(raw: unknown): Record<string,
unknown>`. Она возвращает собственные поля `raw`, которых нет в `Settings`, в порядке `raw`; если `raw` —
не объект, возвращает `{}`. `getSettings` собирает результат так:
`{ ...coerceSettings(raw, DEFAULT_SETTINGS), ...extraSettingFields(raw) }`, где `raw` — значение записи под
ключом настроек (или `undefined`, если записи нет).

**Rationale**:
- Прежнее чтение — `{ ...DEFAULT_SETTINGS, ...raw }`: сначала 13 полей в порядке `DEFAULT_SETTINGS`, затем
  неизвестные поля `raw` в его порядке. Новая сборка даёт тот же порядок ключей: `coerceSettings` копирует
  `DEFAULT_SETTINGS`, а неизвестные поля добавляются после. На корректных данных результат совпадает
  и по значениям, и по порядку ключей. Порядок важен для экспорта: `buildBackup` пишет настройки в файл
  через `JSON.stringify`.
- `updateSettings` накладывает изменение на `getSettings()` и пишет запись целиком. Раз неизвестные поля
  остаются в результате чтения, они не теряются при изменении настроек (пункт файла шага).
- `extraSettingFields` строит объект через `Object.fromEntries`, а не присваиванием по ключу, поэтому ключ
  `__proto__` из данных не меняет прототип. Прежний spread вёл себя так же.
- Две функции вместо одной «чтение из базы» оставляют вызов прозрачным. В `getSettings` видны оба
  правила: поля проверяются, неизвестные сохраняются. Причина второго правила (запись настроек целиком)
  живёт в хранилище.

**Alternatives considered**:
- *Флаг `coerceSettings(raw, fallback, { keepUnknown: true })`*: логический параметр меняет семантику
  функции. Две функции с ясными именами проще.
- *`coerceSettings` всегда сохраняет неизвестные поля `raw`*: импорт стал бы переносить в базу
  неизвестные поля из файла. Это изменение поведения импорта (FR-003), отклонено.
- *Отдельная функция `coerceStoredSettings(raw)` в домене*: тоже допустимо, но тогда правило «неизвестные
  поля сохраняются, потому что настройки пишутся целиком» уезжает в домен, далеко от своей причины.

## R3. Что меняется для некорректно сохранённых настроек

**Decision**: известное поле с некорректным значением при чтении заменяется значением по умолчанию. При
ближайшем `updateSettings` в базу пишется уже приведённое значение. Отдельной «починки» базы при запуске
нет.

**Rationale**:
- Значения, которые сохраняет само приложение, правилам соответствуют. Степперы настроек (`Stepper` в
  `SettingsScreen`) берут `min`/`max` из тех же доменных констант, шагают по ±1 и блокируют кнопки на
  границах. Переключатели пишут логические значения. Миграции v2–v6 добавляют недостающие поля с
  корректными значениями. Существующие тесты (`db.test.ts`, `update.test.ts`, `backup.test.ts`,
  `upgrade-v2.test.ts`, `textImport.test.ts`, `atomicWrites.test.ts`, `useLiveQuery.test.ts`, UI-тесты)
  сохраняют только корректные значения, поэтому ни одна их проверка не меняется.
- Значит, некорректное поле в базе возможно только при порче данных или ошибке будущего кода. Сейчас
  такой мусор доходит до `buildForecast` и планировщика напоминаний (`push/sync.ts` читает через
  `getSettings`) и может уронить отрисовку. Значение по умолчанию — это цель шага.
- Запись приведённого значения при изменении настроек — та же модель, что у записи дня (образец шага):
  `updateDayEntry` и `saveDayEntry` пишут запись, приведённую `coerceDayEntry`, и непонятные части
  становятся пустыми (009 FR-003). В базе оказывается то, что пользовательница видела на экране. Мусор
  не несёт смысла, преобразовать его не во что, а неизвестные поля, которые могут нести смысл для
  будущей версии, сохраняются (R2).
- Экспорт (`buildBackup` → `getSettings`) тоже отдаёт приведённые значения. Раньше мусор уходил в файл, а
  при импорте всё равно заменялся значением устройства.

**Alternatives considered**:
- *Писать в `updateSettings` «сырую» запись поверх изменения* (`{ ...raw, ...patch }`): мусор сохранялся
  бы в базе навсегда и приводился бы при каждом чтении. Это второй путь записи с другой семантикой,
  чем у записи дня. Отклонено.
- *Запасное значение — последнее корректное*: у приложения его нет; хранить историю настроек ради
  порченых данных — лишнее (Конституция V).

## R4. Строгая проверка месячных: `validatePeriods` с кодами ошибок

**Decision**: новый файл `src/domain/periodValidation.ts`:
`validatePeriods(input: unknown, today: LocalDate, periodLength: number): Result<Period[], PeriodValidationError>`.
Внутри два этапа в прежнем порядке:

1. По каждой записи в порядке входа, до первой ошибки (бывший `parsePeriods`): список → объект →
   идентификатор (непустая строка) → уникальность идентификатора → дата начала → дата конца (`null` или
   дата) → `endEstimated` логическое → конец не раньше начала → длина не больше `MAX_PERIOD_DAYS`. Из
   записи берутся только `id`, `start`, `end`, `endEstimated`.
2. Объединение (бывший `mergeImported`): `normalizePeriods(periods, today, periodLength)`, затем — ошибка,
   если у соседних по порядку месячных `periodEnd(предыдущих) >= start(следующих)`, т. е. они
   пересекаются (объединить их не дал лимит 15 дней). Соприкосновение без пересечения ошибкой не
   считается, как и сейчас.

`PeriodValidationError` — размеченное объединение по полю `code` (полный список и тексты — `data-model.md`).
Готовых текстов в домене нет. `backup.ts` вызывает `validatePeriods(data.periods, toLocalDate(new Date()),
settings.defaultPeriodLength)` и превращает код в прежний текст функцией `periodErrorText` (`switch` по
`code`), затем оборачивает его в `corrupted(...)`.

**Rationale**:
- Одна функция с прежним порядком проверок: первой сообщается та же ошибка, что и раньше, а `backup.ts`
  делает один вызов. Оба этапа — правила домена (003 FR-015: объединять можно не всё).
- «Сегодня» — параметром (Конституция IV). Текущее время читает `backup.ts`, как и раньше
  (`toLocalDate(new Date())`); слой хранения это может.
- Коды точнее текстов: «некорректный» и «повторный» идентификатор — разные коды (`invalid-id`,
  `duplicate-id`) с одним прежним текстом. Параметры — ровно то, что нужно тексту: исходное значение
  поля (текст строится через `String(...)`, как раньше), дата начала, даты пересекающихся месячных и
  лимит длины (`maxDays`, чтобы `backup.ts` не импортировал `MAX_PERIOD_DAYS` ради текста).
- Тип результата — существующий `Result<T, E>` из `types.ts`.

**Alternatives considered**:
- *Две функции (`checkPeriods` и проверка пересечений)*: `backup.ts` делал бы два вызова и две проверки
  результата, а порядок этапов задавал бы вызывающий. Одна функция надёжнее, порядок закреплён в домене.
- *Добавить в `src/domain/periods.ts`*: там правила редактирования месячных (`markPeriodStart` и др.) с
  кодами `PeriodError` для интерфейса. Проверка внешнего списка — другая задача. Отдельный файл держит
  `periods.ts` прежним и даёт отдельный файл тестов.
- *Коды в `PeriodError` (`types.ts`)*: у тех кодов нет параметров, и они относятся к действиям в
  интерфейсе; смешивать два назначения незачем.

## R5. Месячные при чтении из базы не проверяются

**Decision**: `getPeriods` не меняется; `validatePeriods` вызывается только при импорте резервной копии.

**Rationale**: `savePeriods` переписывает таблицу целиком (`repository.ts`, «Что решено не менять»). Запись,
отброшенная при чтении, была бы удалена при следующем сохранении месячных — нарушение Конституции III.
Некорректные месячные при чтении — зона аварийного экрана (шаг 1). Мягкое чтение месячных — вне объёма
шага («Границы»).

## R6. Один ключ настроек

**Decision**: в `src/storage/repository.ts` константа становится экспортируемой:
`export const SETTINGS_KEY = 'settings'`. `applyBackup` в `backup.ts` пишет `{ key: SETTINGS_KEY, ... }`.
Литералы в блоках `this.version(2…6)` файла `db.ts` не меняются. Литерал в `src/push/sync.ts`
(`liveQuery` на изменения) — зона шага 5, не меняется.

**Rationale**:
- `backup.ts` уже импортирует `repository.ts`, поэтому новой зависимости нет. Остальные ключи (`push`,
  `devMode`, `firstPeriodHintDismissed`) нужны только репозиторию и остаются в нём закрытыми.
- `db.ts` — замороженная история миграций (Общие ограничения, п. 4); туда константа не нужна.

**Alternatives considered**:
- *Константа в `db.ts`*: модуль схемы стал бы хранить ключи записей `kv`; блоки миграций всё равно её не
  используют. Отклонено.
- *Константа в домене*: ключ записи в базе — деталь хранения, не правило домена.

## R7. Одна проверка «это объект»

**Decision**: новый файл `src/domain/guards.ts` с
`export const isObject = (v: unknown): v is Record<string, unknown> => typeof v === 'object' && v !== null && !Array.isArray(v)`.
Его используют `dayEntry.ts` (вместо `isRecord`), `settings.ts`, `periodValidation.ts` и `backup.ts`
(вместо своего `isObject`).

**Rationale**:
- Тело у `isRecord` и `isObject` одинаковое, поведение не меняется.
- Отдельный файл не тянет лишнего: `settings.ts` не должен импортировать модуль записи дня ради одной
  функции. `storage` может импортировать `domain` (правила слоёв).
- `src/storage/migrations/index.ts` проверяет `typeof settings !== 'object' || settings === null` — это
  другая семантика (списки проходят). Её замена изменила бы миграции, поэтому миграции не трогаются;
  это записывается в «Журнал» как находка.

## R8. Тексты ошибок импорта — символ в символ

**Decision**: до переноса пишется характеризационный тест `src/storage/backupRules.test.ts`. Для каждого
отказа импорта месячных он проверяет точный текст (`toBe`), а не только префикс. Тест зелёный до и после
переноса. Случаи: нет списка; запись не объект (`null`, список, строка); `id` не строка, пустой, повторный;
некорректная дата начала; некорректная или отсутствующая дата конца; нет `endEstimated` и он не
логический; конец раньше начала; месячные длиннее 15 дней; пересечение, которое нельзя объединить. Там же —
характеризация настроек при импорте: неизвестные поля файла отбрасываются, неизвестные поля настроек
устройства сохраняются, первая ошибка — по порядку записей.

**Rationale**: `backup.test.ts` для повреждённых месячных проверяет только префикс
`/^Файл резервной копии повреждён/`, поэтому изменение хвоста текста он бы не заметил. Менять его нельзя
(FR-015), значит нужен новый файл.

## R9. Порядок работы и тесты

**Decision**: тесты — только в новых файлах, существующие не меняются:

| Файл | Окружение | Что | До кода |

| `src/storage/settingsRead.test.ts` | node + `fake-indexeddb/auto` | чтение настроек: корректные данные с неизвестными полями и порядок ключей, `updateSettings` не теряет неизвестные поля — зелёные до кода; некорректное поле, не объект → значения по умолчанию, `updateSettings` пишет приведённое — падают до кода | частично |
| `src/domain/guards.test.ts` | node | `isObject` | падает (нет модуля) |
| `src/domain/settings.test.ts` | node | `coerceSettings` по каждому из 13 полей, не объект, неизвестные поля, новый объект; `extraSettingFields` | падает |
| `src/domain/periodValidation.test.ts` | node | каждый код ошибки с параметрами, порядок, корректный список, объединение, «сегодня» | падает |
| `src/storage/validationPlacement.test.ts` | node | по исходникам: в `backup.ts` нет правил по полям и своего `isObject`; литерал `'settings'` в `repository.ts` и `backup.ts` — один, в определении константы; в `dayEntry.ts` нет `isRecord` (FR-010–FR-012) | падает |

проверяет FR-013.

**Rationale**: Конституция IV и «Общие ограничения», п. 5: новая функция — сначала падающий тест; перенос —
сначала характеризационный тест. Красный коммит не прошёл бы `npm test`, поэтому тест и код идут в одном
коммите, а падение проверяется до кода.

## R10. Зависимости и производительность

**Decision**: новых зависимостей нет. Чтение настроек — одна запись `kv`; приведение — 13 проверок и проход
по ключам. Разницы не заметно.
