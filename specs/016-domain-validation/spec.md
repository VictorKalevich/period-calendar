# Feature Specification: Правила корректности настроек и месячных — в домене

**Feature Branch**: `016-domain-validation`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Рефакторинг: правила корректности настроек и месячных переносятся в доменный
модуль. Сейчас запись дня проверяется одной доменной функцией на всех путях (чтение, запись, импорт,
миграция), а правила для настроек и месячных написаны в модуле резервной копии слоя хранения и применяются
только при импорте; настройки из базы читаются без проверки. Нужно: чистые доменные функции проверки
настроек (по полям, с запасным значением) и месячных (строгая проверка с кодами ошибок), покрытые
собственными тестами; импорт резервной копии использует их и сохраняет прежние тексты ошибок; настройки при
чтении из базы приводятся теми же правилами, не теряя неизвестных полей. Месячные при чтении не
фильтруются. Поведение на корректных данных, формат резервной копии, схема хранения и тексты не меняются;
существующие тесты не изменяются и остаются зелёными. Подробности и границы —
docs/refactoring/step-3-domain-validation.md и docs/refactoring-roadmap.md."

Шаг 3 плана рефакторинга (`docs/refactoring-roadmap.md`, `docs/refactoring/step-3-domain-validation.md`).
Видимых изменений нет.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Испорченная настройка в базе не ломает экран (Priority: P1)

Настройки читаются из базы теми же правилами, что и при импорте резервной копии: каждое поле проверяется
отдельно, некорректное или отсутствующее заменяется значением по умолчанию. Испорченная запись (например,
нечисловая длина цикла) больше не доходит до прогноза и не роняет отрисовку. На корректных данных
прочитанные настройки — те же, что раньше, включая поля, которых приложение не знает.

**Why this priority**: сейчас настройки из базы читаются без проверки — мусор в одном поле дошёл бы до
расчёта прогноза и уронил экран; данные существуют только на устройстве (Конституция III).

**Independent Test**: на изолированной базе записать настройки с одним некорректным полем и прочитать их —
это поле равно значению по умолчанию, остальные — как в базе; на корректных настройках с неизвестным полем
результат совпадает с прежним чтением.

**Acceptance Scenarios**:

1. **Given** в базе корректные настройки, **When** они читаются, **Then** результат совпадает с прежним
   чтением (значения по умолчанию, поверх них сохранённые значения), включая неизвестные поля и порядок
   полей.
2. **Given** в базе у одного известного поля некорректное значение (не того типа, вне диапазона, дробное
   там, где нужно целое), **When** настройки читаются, **Then** это поле равно значению по умолчанию,
   остальные — сохранённые.
3. **Given** в базе нет настроек, **When** они читаются, **Then** результат — настройки по умолчанию, как
   сейчас.
4. **Given** в базе вместо настроек не объект (строка, число, список, `null`), **When** настройки
   читаются, **Then** результат — настройки по умолчанию.
5. **Given** в базе настройки с неизвестным полем, **When** меняется одна настройка, **Then** неизвестное
   поле остаётся в базе.
6. **Given** в базе некорректное известное поле, **When** меняется другая настройка, **Then** в базу
   записывается значение по умолчанию вместо некорректного, изменённая настройка — новая.

### User Story 2 - Импорт резервной копии ведёт себя как раньше (Priority: P1)

Импорт резервной копии принимает и отклоняет те же файлы, что и раньше, с теми же текстами ошибок символ в
символ, и даёт тот же результат: месячные проверяются строго, настройки — по полям с запасным значением
устройства, записи дней — мягко.

**Why this priority**: шаг — рефакторинг; видимых изменений быть не должно (Общие ограничения, п. 1).
Тексты ошибок импорта видит пользовательница.

**Independent Test**: для каждого случая отказа импорта зафиксировать точный текст ошибки до переноса
правил — после переноса тексты те же; существующие тесты резервной копии не изменены и зелёные.

**Acceptance Scenarios**:

1. **Given** файл с некорректными месячными (нет списка; запись не объект; некорректный или повторный
   идентификатор; некорректная дата начала или конца; нет признака оценки конца; конец раньше начала;
   месячные длиннее 15 дней; пересечение, которое нельзя объединить), **When** он импортируется, **Then**
   импорт отклонён с тем же текстом ошибки, что и раньше, символ в символ.
2. **Given** файл с некорректным полем настроек, **When** он импортируется, **Then** это поле берётся с
   устройства, остальные — из файла, как раньше.
3. **Given** файл с полем настроек, которого приложение не знает, **When** он импортируется, **Then** поле
   не попадает в результат, как раньше.
4. **Given** корректный файл, **When** он импортируется, **Then** месячные, записи дней, настройки и
   итог («сколько месячных и записей») — те же, что раньше.

### User Story 3 - Правила проверяются отдельно от разбора файла (Priority: P2)

Правила корректности настроек и месячных — инварианты домена — описаны в доменном модуле рядом с
диапазонами, из которых они следуют, и проверяются собственными тестами без базы и без файла резервной
копии. Проверка месячных сообщает, что именно не так, кодом ошибки с параметрами, а не готовым текстом.

**Why this priority**: облегчает дальнейшие шаги и любые новые пути записи; само по себе не меняет
поведение.

**Independent Test**: тесты домена вызывают проверку настроек и месячных напрямую: каждое поле настроек —
корректное значение принимается, некорректное заменяется запасным; для месячных — каждый код ошибки.

**Acceptance Scenarios**:

1. **Given** для каждого поля настроек корректное и некорректное значение, **When** выполняется проверка
   с запасными настройками, **Then** корректное принимается, некорректное заменяется запасным.
2. **Given** месячные с ошибкой каждого вида, **When** выполняется строгая проверка, **Then** результат —
   отказ с кодом этой ошибки и её параметрами (значение поля, дата начала, лимит); первой сообщается
   первая по порядку записей ошибка, как сейчас.
3. **Given** корректные месячные, **When** выполняется строгая проверка, **Then** результат — те же
   месячные только с полями периода.

### Edge Cases

- Сохранённое поле настроек со значением `undefined` (поле есть, значения нет) — значение по умолчанию.
- Числовое поле настроек: `NaN`, `Infinity`, строка с числом (`'30'`), дробное, на границе диапазона и за
  ней — принимаются только целые в диапазоне, границы включительно (как при импорте сейчас).
- Логическое поле настроек: `0`, `1`, `'true'`, `null` — некорректны, значение по умолчанию.
- Неизвестные поля настроек при чтении сохраняются (в том числе при последующем изменении настроек и при
  экспорте), при импорте из файла — отбрасываются, как сейчас; неизвестные поля настроек устройства при
  импорте сохраняются, как сейчас.
- Месячные при чтении из базы не проверяются и не фильтруются: запись, отброшенная при чтении, была бы
  удалена при следующем сохранении месячных (запись месячных целиком — «Что решено не менять»).
  Некорректные месячные при чтении — зона аварийного экрана (шаг 1).
- Месячные в файле — в любом порядке; ошибка — по первой некорректной записи в порядке файла.
- Лишние поля у записи месячных в файле отбрасываются, как сейчас.
- Непредвиденная ошибка при импорте по-прежнему перехватывается и сообщается текстом «Файл резервной
  копии повреждён: …» (009 FR-006).

## Requirements *(mandatory)*

### Functional Requirements

**Правила настроек**

- **FR-001**: Правила корректности полей настроек MUST быть чистой функцией доменного модуля: на входе
  любое значение и запасные настройки; на выходе — корректные настройки, где каждое известное поле взято
  из входа, если оно корректно, иначе — из запасных. Если вход — не объект, результат — запасные
  настройки.
- **FR-002**: Правила полей MUST быть прежними: длина цикла — целое 21…45, длина месячных — целое 2…10,
  личный сдвиг овуляции — целое −5…+5 (границы включительно, диапазоны из доменных констант); остальные
  поля — логические значения.
- **FR-003**: Импорт резервной копии MUST использовать эту функцию с настройками устройства в роли
  запасных; результат импорта настроек MUST совпадать с прежним, в том числе неизвестные поля файла
  отбрасываются, а неизвестные поля настроек устройства сохраняются.
- **FR-004**: Чтение настроек из базы MUST приводить сохранённое значение теми же правилами с настройками
  по умолчанию в роли запасных. Неизвестные поля сохранённой записи MUST оставаться в результате; порядок
  полей MUST совпадать с прежним чтением (сначала поля настроек по умолчанию, затем неизвестные).
- **FR-005**: Изменение части настроек MUST по-прежнему накладываться на прочитанные настройки и не
  терять неизвестные поля.

**Правила месячных**

- **FR-006**: Строгая проверка месячных из резервной копии (по каждой записи: список, объект,
  идентификатор и его уникальность, даты начала и конца, признак оценки конца, порядок дат, длина не
  больше 15 дней; и пересечения, оставшиеся после объединения) MUST быть чистыми функциями доменного
  модуля; «сегодня» MUST передаваться параметром.
- **FR-007**: Проверка месячных MUST возвращать либо месячные, либо код ошибки с параметрами,
  достаточными для прежнего текста (значение поля, дата начала, даты пересекающихся месячных, лимит
  длины). Готовых текстов в доменном модуле MUST NOT быть.
- **FR-008**: Импорт резервной копии MUST превращать коды в прежние тексты ошибок символ в символ.
- **FR-009**: Месячные при чтении из базы MUST NOT проверяться и фильтроваться.

**Общие части**

- **FR-010**: Ключ, под которым хранятся настройки, MUST быть одной экспортируемой константой для чтения и
  записи настроек в репозитории и для применения резервной копии. Литералы в блоках миграций схемы
  (`this.version(…)` в `src/storage/db.ts`) MUST NOT меняться; синхронизация напоминаний
  (`src/push/sync.ts`) — зона шага 5 и не меняется.
- **FR-011**: Проверка «значение — обычный объект (не `null` и не список)» MUST быть одной общей функцией
  доменного модуля вместо двух одинаковых (в записи дня и в резервной копии).
- **FR-012**: Модуль резервной копии MUST NOT содержать правил по полям: только разбор файла, миграции,
  тексты ошибок и вызовы домена.
- **FR-013**: Новые файлы доменного модуля MUST NOT импортировать хранилище, интерфейс, push и не читать
  текущее время (охраняет существующий тест изоляции домена).

**Общие ограничения рефакторинга** (`docs/refactoring-roadmap.md`)

- **FR-014**: Поведение и дизайн MUST NOT меняться: разметка, классы, тексты, порядок элементов, формат
  резервной копии, схема IndexedDB, формат запросов к воркеру — прежние. Единственное изменение поведения
  — чтение некорректно сохранённого поля настроек (значение по умолчанию вместо мусора, FR-004).
- **FR-015**: Существующие тесты MUST оставаться зелёными; существующие проверки MUST NOT удаляться или
  ослабляться (допустима только смена путей импорта при переносе кода). В частности,
  `src/storage/backup.test.ts`, `repository.test.ts`, `migrations/migrations.test.ts`,
  `upgrade-v2.test.ts` не меняются (кроме путей импорта). Если нужно изменить существующую проверку —
  остановиться и спросить пользователя.
- **FR-016**: Схема хранения MUST NOT меняться: `SCHEMA_VERSION`, таблицы, форма хранимых записей и блоки
  `this.version(1…6)` в `src/storage/db.ts` — прежние; `worker/` не затрагивается.
- **FR-017**: Правила `CLAUDE.md` и Конституции MUST соблюдаться: TDD (новая функция — сначала падающий
  тест; перенос кода — сначала характеризационный тест, зелёный до и после переноса), правила слоёв
  («Целевые правила слоёв» в плане рефакторинга), «сегодня» — параметром, файлы — UTF-8 без BOM, правка
  только Edit/Write. Новые runtime- и dev-зависимости MUST NOT добавляться.
- **FR-018**: Объём — только этот шаг. Не входят: мягкое чтение месячных, изменение формата резервной
  копии, новые версии схемы, перенос сценариев импорта из хранилища в другой слой, тексты ошибок,
  синхронизация напоминаний (шаг 5). Попутные находки записываются в «Журнал»
  `docs/refactoring-roadmap.md`, а не исправляются.

### Key Entities

- **Настройки**: длина цикла и месячных по умолчанию, личный сдвиг овуляции, переключатели разделов,
  напоминаний и режима расчёта овуляции. Хранятся одной записью; могут содержать поля, которых приложение
  не знает.
- **Месячные**: идентификатор, дата начала, дата конца или её отсутствие, признак «конец проставлен
  автоматически».
- **Ошибка проверки месячных**: код вида ошибки и параметры (значение поля, дата начала, даты
  пересекающихся месячных, лимит длины); текст для пользовательницы строится из неё вне домена.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для каждого из 13 полей настроек тест домена, написанный до кода, подтверждает: корректное
  значение принимается, некорректное заменяется запасным.
- **SC-002**: Для каждого кода ошибки месячных есть тест домена, написанный до кода.
- **SC-003**: Каждый текст ошибки импорта месячных совпадает с прежним символ в символ — подтверждается
  характеризационным тестом, зелёным до и после переноса.
- **SC-004**: Чтение корректных настроек, в том числе с неизвестным полем, даёт тот же результат, что
  раньше (значения и порядок полей); чтение настроек с некорректным полем даёт значение по умолчанию —
  подтверждается тестами на изолированной базе.
- **SC-005**: В модуле резервной копии нет правил по полям; ключ настроек записан одной константой в
  репозитории и резервной копии; проверка «это объект» — одна.
- **SC-006**: Все тесты зелёные, их не меньше базовых 695; существующие проверки не изменены; тест
  изоляции домена зелёный; сборка зелёная.

## Assumptions

- Интерфейс настроек ограничивает значения теми же доменными диапазонами, поэтому значения, сохранённые
  приложением, правилам соответствуют; «некорректное поле» в базе возможно только при порче данных или
  ошибке будущего кода. Проверяется в `research.md`.
- Запасное значение при чтении — настройки по умолчанию (как прежнее чтение для отсутствующих полей), а не
  последнее корректное значение: последнего значения у приложения нет.
- Испорченное поле при чтении в базе не исправляется само: оно заменяется при ближайшем изменении
  настроек (так уже работает наложение изменения на прочитанные настройки).
- Текущее время для объединения месячных при импорте берётся в модуле резервной копии, как сейчас, и
  передаётся в домен параметром.
