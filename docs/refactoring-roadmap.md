# План рефакторинга

Составлен 2026-11-14 по итогам оценки архитектуры (коммит `76b78cb`, ветка `main`).
Каждый шаг выполняется в отдельном чате через Spec Kit. Этот файл — общие правила и статусы;
подробности шага — в `docs/refactoring/step-N-*.md`.

## Как запускать шаг

В новом чате, подставив номер и файл шага из таблицы ниже:

> Прочитай docs/refactoring-roadmap.md и docs/refactoring/step-1-render-failure.md. Выполни шаг 1
> через Spec Kit по разделу «Порядок работы над шагом». В конце обнови статус шага в плане.

Шаг 8 (выпуск) запускается так же, но идёт по своему файлу, а не по разделу «Порядок работы над
шагом»:

> Прочитай docs/refactoring-roadmap.md и docs/refactoring/step-8-release.md. Выполни шаг 8 по
> разделу «Порядок выпуска». В конце обнови статус шага в плане.

## Общие ограничения (для каждого шага)

1. **Поведение и дизайн не меняются.** Разметка, классы, тексты, порядок элементов, формат
   резервной копии, схема IndexedDB, формат запросов к воркеру — прежние. Единственное
   исключение — шаг 1: он добавляет видимое состояние при сбое; на обычном пути и он ничего не меняет.
2. **Тесты остаются зелёными.** Существующие проверки (`expect`) не удаляются и не ослабляются.
   В существующих тестах допускается менять только пути импорта при переносе кода. Если шаг требует
   изменить существующую проверку — остановиться и спросить пользователя.
3. **Правила `CLAUDE.md` и Конституции обязательны** (`.specify/memory/constitution.md`): домен —
   чистые функции, «сегодня» параметром; TDD; новая runtime-зависимость — только с обоснованием в
   плане; изменения схемы Dexie — версия + миграция + тест; UI — только из дизайн-системы; файлы
   править только Edit/Write; перед коммитом проверять `git diff` на испорченную кириллицу и BOM.
4. **Схему хранения рефакторинг не трогает.** Ни один шаг не меняет `SCHEMA_VERSION`, таблицы и
   форму хранимых записей. Блоки `this.version(1…6)` в `src/storage/db.ts` не правятся.
5. **TDD в рефакторинге.** Новая функция или модуль — сначала падающий тест. Перенос существующего
   кода — сначала характеризационный тест на текущее поведение (зелёный и до, и после переноса).
6. **Объём шага — только то, что в его файле.** Попутные находки записываются в раздел «Журнал»
   этого файла, а не исправляются.

## Ветки и запрет на push (исключение из `CLAUDE.md`)

Пользователь явно задал правило для этого рефакторинга: **`git push origin main` и любой деплой
выполняются только в шаге 8.** На время рефакторинга это отменяет пункты `CLAUDE.md` «слить ветку
фичи в `main` и выполнить `git push origin main` без отдельного вопроса» и «задеплоить воркер
`npx wrangler deploy` до push».

- Вся работа копится в ветке **`refactoring`** (создаётся от `main` в первом выполняемом шаге).
  Локальный `main` до шага 8 не меняется — он остаётся равен `origin/main`, поэтому случайный push
  ничего не выкатит.
- Ветка фичи шага создаётся от `refactoring` и после проверок сливается в `refactoring`
  (не в `main`), затем удаляется локально.
- До шага 8 не выполнять: `git push` (ни `main`, ни других веток), `npx wrangler deploy`,
  удаление веток на origin. Если нужна резервная копия ветки `refactoring` на GitHub — это решает
  пользователь (push ветки, отличной от `main`, деплой не запускает).
- Обычные фичи во время рефакторинга лучше не начинать: каталоги `specs/NNN-…` нумеруются по
  порядку, и фича от `main` получит тот же номер, что и шаг в `refactoring`. Если фича всё же
  нужна — после её выхода влить `main` в `refactoring` и при совпадении номера переименовать
  каталог спецификации шага.

## Порядок работы над шагом

Выполнять по порядку. Команды `npm …` запускать из PowerShell в папке проекта (из Git Bash с
`cd /c/…` Vitest не стартует — это особенность окружения, не поломка тестов).

1. **Прочитать**: `CLAUDE.md`, `.specify/memory/constitution.md`, этот файл, файл шага. Если шаг
   затрагивает UI — `docs/design/design.md`.
2. **Проверить готовность**: статус шага — `не начат`; шаги из колонки «Зависит от» — `выполнен`
   или `исключён`. Иначе остановиться и сообщить пользователю.
3. **Перейти в `refactoring`**:
   - ветки нет — `git switch -c refactoring main`;
   - ветка есть — `git switch refactoring`; если `main` ушёл вперёд — `git merge main`
     (конфликт — остановиться и сообщить);
   - если `docs/refactoring-roadmap.md` и `docs/refactoring/` ещё не закоммичены — закоммитить их
     первым коммитом в `refactoring` («рефакторинг: план и шаги»);
   - рабочее дерево чистое (неотслеживаемая папка `Claude outputs/` не в счёт).
4. **Базовая линия**: `npm test`, `npm run build`; если шаг затрагивает `worker/` —
   `npm test --prefix worker` и `npm run typecheck --prefix worker`. Записать число тестов. Красное —
   остановиться и сообщить.
5. **Поставить статус `в работе`** в таблице выше и закоммитить.
6. **Spec Kit**, по порядку: `/speckit-specify` (текст — раздел «Описание для /speckit-specify» из
   файла шага) → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`.
   - Ветка фичи — от `refactoring`. Если `/speckit-specify` не создал ветку сам —
     `git switch -c <NNN-короткое-имя> refactoring`, имя — как у каталога `specs/NNN-…`.
   - В спецификацию перенести «Общие ограничения» этого файла и «Границы» с «Критериями готовности»
     из файла шага как требования и критерии успеха.
   - Раздел «Набросок решения» в файле шага — отправная точка, а не предписание: окончательное
     устройство определяет `/speckit-plan`. Пункты «Проверить на этапе плана» разобрать в `research.md`.
   - Маленькие коммиты; каждый проходит `npm test` и `npm run build`.
7. **Проверки после реализации**:
   - `npm test`, `npm run build`; при изменениях в `worker/` — `npm test --prefix worker` и
     `npm run typecheck --prefix worker`;
   - число тестов не меньше базового; существующие проверки не изменены (см. «Общие ограничения», п. 2);
   - критерии готовности из файла шага выполнены;
   - `git diff refactoring...HEAD` — без испорченной кириллицы и BOM, без изменений вне объёма шага.
   Если что-то красное — ничего не сливать, сообщить пользователю.
8. **Слить в `refactoring`**: `git switch refactoring`, `git merge --no-ff <ветка-шага>`, повторить
   `npm test` и `npm run build`, затем `git branch -d <ветка-шага>`. **Не выполнять** `git push`,
   `npx wrangler deploy` и слияние в `main`.
9. **Обновить план**: в таблице — статус `выполнен`; в «Журнале» — дата, каталог `specs/NNN-…`,
   хэш коммита слияния, число тестов до и после, отступления от файла шага и попутные находки.
   Закоммитить в `refactoring`.
10. **Сообщить пользователю**: что сделано, результаты проверок, что отложено, команда для
    следующего шага.

## Что решено не менять

- **Запись месячных целиком** (`savePeriods` — очистка и запись всей таблицы из результата
  `PeriodAction.apply()`). Действия открываются в модальном листе по свежему снимку данных, окно
  одно; перевод на транзакционное обновление потребовал бы менять контракт `PeriodAction` и
  большой объём доменных тестов ради гонки, которой на практике нет.
- **Мягкое чтение месячных не вводить.** Раз таблица переписывается целиком, отфильтрованные при
  чтении «некорректные» записи были бы удалены при следующей записи — нарушение Конституции III.
- **Отдельный слой «use cases» между UI и хранилищем не вводить.** Приложение — около 5 тыс. строк;
  прямые вызовы `repository` из компонентов проще и соответствуют Конституции V (YAGNI).
- **Блоки миграций `this.version(2…5)` в `db.ts`** — повторяются, но это замороженная история.
- **`app.css` одним файлом (935 строк)** — токены охраняет `design-system.test.ts`; дробление —
  косметика.
- **`memo` у `DayCell`** фактически не срабатывает (`dayInfo` каждый раз возвращает новый объект),
  но перерисовка до 126 ячеек на нажатие не заметна; оптимизация не нужна.
- **Линтер (ESLint)** не добавляется: правила слоёв закрывает тест шага 7.

## Вне плана — нужны отдельные решения пользователя

Это не рефакторинг: меняется поведение, формат обмена или инфраструктура.

1. **Идентификатор напоминания раскрывает его вид.** На сервер намеренно не уходит поле `kind`
   (`src/domain/reminders.ts:87-93`, 007 FR-009), но уходит `id` вида `ovulation:2026-11-05`,
   `period:…`, `missed-period:…` (`reminders.ts:45,67,71`), который несёт ту же информацию и
   хранится в KV. Спецификация 007 разрешает `id` «как сейчас», так что формально нарушения нет,
   но цель — не раскрывать вид — не достигнута. Решение — непрозрачный `id`; это правка
   спецификации 007.
2. **Постоянный отказ синхронизации не виден.** Любой ответ воркера, кроме 2xx (в том числе 400 и
   401), ставит `pendingSync` (`src/push/sync.ts:50-54`); интерфейс бесконечно показывает
   «расписание отправится при подключении к интернету» (`RemindersSection.tsx:61`).
3. **Воркер деплоится вручную, приложение — из CI.** Возможен рассинхрон версий; автоматический
   деплой воркера требует токена Cloudflare в секретах GitHub.
