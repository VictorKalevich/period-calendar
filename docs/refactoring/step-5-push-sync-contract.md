# Шаг 5. Напоминания: контракт с воркером под тестом, синхронизация без гонок

Приоритет: средний. Зависимости: нет. Видимых изменений нет.
Общие правила и порядок работы — `docs/refactoring-roadmap.md`.

**Шаг затрагивает `worker/`.** Деплой воркера (`npx wrangler deploy`) в этом шаге не выполняется —
он откладывается до шага 8.

## Проблема

1. **Контракт приложения и воркера ничем не проверяется.** Ограничения запроса живут только в
   воркере (`worker/src/validate.ts:5-11`: до 24 напоминаний, `title` ≤ 100, `body` ≤ 200,
   `id` ≤ 64, не дальше 400 дней). В приложении лимит 24 продублирован константой
   (`src/domain/reminders.ts:35`), остальные не известны вовсе. Нет теста, что расписание из
   `toServerReminders(planReminders(...))` проходит `validatePutBody`. Нарушение даёт ответ 400,
   приложение ставит `pendingSync` (`src/push/sync.ts:50-54`), и напоминания молча перестают
   приходить.
2. **Состояние push пишется из устаревшего снимка.** `doSync` читает состояние
   (`sync.ts:28`), ждёт сеть (`sync.ts:45-49`) и записывает `{ ...state, … }`
   (`sync.ts:32,51,53`). Если за это время напоминания выключили (`src/push/subscribe.ts:64-76`),
   завершившаяся синхронизация вернёт `subscribed: true`. То же в `subscribe.ts:52-59`.
3. **Изменение во время синхронизации не отправляется.** `syncReminders` возвращает уже идущий
   запрос (`sync.ts:21-24`), собранный по старым данным; новое расписание уйдёт только при
   следующем событии (сеть, возврат в приложение, ещё одно изменение).
4. **`push/sync.ts` обращается к базе в обход репозитория**: импорт `db` (`sync.ts:5`) и литерал
   ключа `'settings'` (`sync.ts:65`).
5. **У `src/push` нет ни одного теста**: логика синхронизации сцеплена с `fetch`,
   `navigator.serviceWorker` и `import.meta.env`.
6. **Сбой на одной записи останавливает рассылку всем.** В `runSchedule`
   (`worker/src/index.ts:183-211`) чтение KV с разбором JSON и запись выполняются без `try/catch`
   на запись: повреждённая запись или отказ KV прерывает обход оставшихся подписок.
7. **Документ контракта устарел**
   (`specs/001-cycle-calendar/contracts/push-worker-api.md`): в CORS нет `POST` (в коде есть —
   `index.ts:47`); payload описан как `{ title, body }` (в коде `{ title, body, id }` —
   `index.ts:198`, `src/sw.ts:27-33`); в примере заголовок «Овуляция», заменённый в фиче 007;
   `VAPID_SUBJECT` назван переменной, а по `worker/wrangler.toml:21` это секрет.

## Цель

Расхождение приложения и воркера ловится тестом; состояние подписки не затирается; последнее
изменение расписания всегда отправляется; сбой одной подписки не мешает остальным.

## Набросок решения

1. **Контрактный тест**: расписание, построенное доменом для всех видов напоминаний и граничных
   настроек, проходит `validatePutBody` воркера; payload воркера соответствует тому, что читает
   `src/sw.ts`.
2. **Ядро синхронизации с внедряемыми зависимостями** (чтение и изменение состояния, получение
   подписки, `fetch`, часы) — чтобы его можно было тестировать без браузера. `sync.ts` остаётся
   тонкой обвязкой.
3. `updatePushState(patch)` в репозитории — транзакционно, по образцу `updateSettings`
   (`src/storage/repository.ts:87-92`); после ожидания сети пишутся только изменённые поля.
4. Повторный запуск: запрос синхронизации во время идущей приводит к ещё одному проходу после её
   завершения.
5. Подписка на изменения — через функции репозитория (`getPeriods`, `getSettings`) внутри
   `liveQuery`, без импорта `db` и литерала ключа.
6. `runSchedule`: обработка каждой записи в своём `try/catch`; в лог — только имя шага и причина,
   без endpoint и текстов (правило из шапки `worker/src/index.ts`).
7. Обновить документ контракта по коду.

## Проверить на этапе плана

- **Где жить контрактному тесту.** Тест в `src/` с импортом `worker/src/validate.ts` втянет в
  проверку типов приложения `worker/src/webpush.ts` (через `import type`), а там есть тип
  `SubtleCryptoDeriveKeyAlgorithm` из `@cloudflare/workers-types`, которого нет в `tsconfig.json`
  приложения. Варианты: вынести `PushSubscriptionJSON` из `webpush.ts`, чтобы `validate.ts` не
  зависел от него; либо разместить тест в `worker/test` и импортировать домен приложения
  (проверить разрешение `date-fns` и типы `crypto` в `worker/tsconfig.json`). Выбрать вариант, при
  котором `npm run build` и `npm run typecheck --prefix worker` остаются зелёными.
- Правило слоёв: `worker/` не импортирует `src/` в рабочем коде; исключение допустимо только для
  теста и должно быть названо в плане.
- Поведение при ответах 4xx остаётся прежним (ставится `pendingSync`) — различать постоянный и
  временный отказ здесь не нужно, это вынесено в «Вне плана».

## Границы

Входит: пункты 1–7 наброска.

Не входит: формат `id` напоминаний, тексты и расписание напоминаний, новый интерфейс для ошибок
синхронизации, изменение HTTP-контракта и ограничений воркера, автоматический деплой воркера,
деплой в этом шаге.

## Критерии готовности

- Контрактный тест написан до правок и проходит для напоминаний о месячных, овуляции и
  неотмеченном начале.
- Тесты ядра синхронизации, написанные до кода: выключение во время синхронизации не отменяется;
  изменение во время синхронизации отправляется повторным проходом; без сети ставится
  `pendingSync`; неизменное расписание повторно не отправляется.
- В `src/push` нет импорта `storage/db` и литерала `'settings'`.
- Тест воркера: повреждённая запись подписки не мешает отправке остальным.
- `worker/test/api.test.ts` и `worker/test/webpush.test.ts` не изменены (кроме путей импорта) и
  зелёные.
- Документ контракта соответствует коду.
- `npm test`, `npm run build`, `npm test --prefix worker`, `npm run typecheck --prefix worker`
  зелёные.
- В «Журнале» плана отмечено, меняет ли шаг рабочий код `worker/src` (нужно шагу 8 для решения о
  деплое воркера).
