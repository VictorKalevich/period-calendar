# Шаг 3. Правила корректности настроек и месячных — в домене

Приоритет: средний. Зависимости: нет. Видимых изменений нет.
Общие правила и порядок работы — `docs/refactoring-roadmap.md`.

## Проблема

У трёх хранимых сущностей три разные политики проверки, а сами правила лежат не в домене.

1. **Запись дня** проверяется везде одной доменной функцией `coerceDayEntry`
   (`src/domain/dayEntry.ts:66-81`): при чтении и записи (`repository.ts:47-72`), импорте
   (`backup.ts:89-100`) и миграции (`migrations/index.ts:72-74`). Это образец.
2. **Настройки** проверяются по полям только при импорте (`SETTING_RULES` и `parseSettings`,
   `src/storage/backup.ts:105-129`). Чтение — приведение типа без проверки
   (`repository.ts:74-77`). Нечисловая длина цикла в базе дошла бы до `buildForecast` и уронила
   отрисовку.
3. **Месячные** строго проверяются только при импорте (`parsePeriods`, `backup.ts:53-70`).
4. **Правила — это инварианты домена** (диапазоны из `src/domain/types.ts:114-118`), но они
   написаны в `storage/backup.ts` вперемешку с русскими текстами ошибок (`backup.ts:36-38`), и
   проверить их отдельно от разбора файла нельзя.
5. **Ключ настроек `'settings'` записан литералом** в `repository.ts:7`, `backup.ts:184`,
   `push/sync.ts:65` и в блоках миграций `db.ts`.
6. Дубли: `isObject` (`backup.ts:50`) и `isRecord` (`dayEntry.ts:17`).

## Цель

Правила корректности настроек и месячных — чистые функции домена с собственными тестами.
Настройки читаются из базы теми же правилами, что и при импорте.

## Набросок решения

1. `src/domain/settings.ts`: `coerceSettings(raw, fallback)` — правила по полям из `SETTING_RULES`
   с той же семантикой, что у `parseSettings` (некорректное или отсутствующее поле — значение из
   `fallback`). Импорт в `backup.ts` использует её.
2. `getSettings` приводит прочитанное через `coerceSettings(raw, DEFAULT_SETTINGS)`.
3. Строгая проверка месячных переносится в домен (`src/domain/periods.ts` или отдельный файл) и
   возвращает **коды** ошибок с параметрами; `backup.ts` превращает коды в прежние русские тексты.
4. Один экспортируемый ключ настроек для `repository.ts` и `backup.ts`. Литералы в блоках
   `this.version(…)` файла `db.ts` не трогать. `push/sync.ts` — зона шага 5.
5. Одна общая проверка «это объект» вместо двух.

## Проверить на этапе плана

- **Неизвестные поля настроек.** Сейчас чтение сохраняет поля, которых нет в `Settings`
  (`{ ...DEFAULT_SETTINGS, ...rec.value }`), а `parseSettings` при импорте их отбрасывает. Для
  чтения поведение должно остаться прежним: неизвестные поля не теряются при последующем
  `updateSettings`. Зафиксировать тестом.
- **Месячные при чтении не фильтровать.** `savePeriods` переписывает таблицу целиком
  (`repository.ts:26-31`): запись, отброшенная при чтении, была бы удалена при следующем
  сохранении — нарушение Конституции III. Некорректные месячные при чтении — зона аварийного
  экрана (шаг 1), а не этого шага.
- Тексты ошибок импорта должны совпасть посимвольно: их проверяет `src/storage/backup.test.ts`.

## Границы

Входит: `coerceSettings`, перенос проверки месячных в домен, чтение настроек через правила, общий
ключ настроек, общий `isObject`.

Не входит: мягкое чтение месячных, изменение формата резервной копии, новые версии схемы,
перенос сценариев импорта из `storage` в другой слой, тексты ошибок.

## Критерии готовности

- Тесты домена, написанные до кода: каждое поле настроек — корректное значение принимается,
  некорректное заменяется значением из `fallback`; для месячных — каждый код ошибки.
- `src/storage/backup.ts` не содержит правил по полям — только разбор файла, миграции, тексты и
  вызовы домена.
- `getSettings` на корректных данных возвращает то же, что раньше, включая неизвестные поля;
  на некорректном поле — значение по умолчанию вместо мусора.
- `src/storage/backup.test.ts`, `repository.test.ts`, `migrations.test.ts`, `upgrade-v2.test.ts`
  не изменены (кроме путей импорта) и зелёные.
- `src/domain/isolation.test.ts` зелёный: новые файлы домена не импортируют `storage`.
- `npm test` и `npm run build` зелёные.
